Modelo entidad-relación de MediAgenda

Cada microservicio es dueño de su propia base de datos PostgreSQL. Dentro de una base, las tablas se unen con llaves foráneas reales; entre bases no hay llaves foráneas: se guardan los códigos y se validan llamando al otro servicio por REST. El modelo sale de las migraciones de Flyway del proyecto.

  • 4bases de datos
  • 8tablas
  • 4llaves foráneas reales
  • 4referencias lógicas entre bases
PK llave primaria FK llave foránea UQ valor único (UQ¹ UQ² UQ³: únicos en pareja) ref código de otra base, sin FK relación con FK relación lógica entre servicios exactamente uno cero o muchos uno o muchos cero o uno

Relaciones

Cómo leerlas: «un médico abre cero o muchas franjas; cada franja es de exactamente un médico».

franja reservada por citas1 : 0..NFK citas.id_franja; como máximo una cita AGENDADA por franja (las demás son canceladas o atendidas)

medicamento se formula en ítems1 : 0..NFK items_formula.id_medicamento. Fórmula y medicamento quedan en relación muchos a muchos a través de items_formula

paciente recibe notificaciones1 : 0..Nlógica notificaciones.codigo_paciente, llega dentro del evento de SQS

Reglas que cuida la base de datos

Restricciones de las migraciones: si el código fallara, la base igual rechaza el dato.

TablaRegla

franjashora_fin > hora_inicio; un médico no repite (fecha, hora_inicio)

medicamentosstock >= 0; nombre y presentación únicos en pareja
items_formulacantidad entre 1 y 100; un medicamento no se repite en la misma fórmula

EstadosCHECK con los valores permitidos de cada estado: cita, franja, triage, fórmula y notificación

Decisiones del modelo

  • Una base por microservicio. Ningún servicio lee las tablas de otro. Así cada uno se despliega, se escala y se migra por separado. El precio: no hay llaves foráneas entre bases, y la integridad entre servicios se valida por REST en el momento de crear el dato.
  • Copias del paciente en citas y fórmulas. nombre_paciente, correo_paciente y telefono_paciente se copian al agendar o formular. Así una cita se puede mostrar y notificar aunque ms-pacientes no responda, y queda el dato tal como estaba en ese momento.
  • Dos identificadores. Llave interna (UUID o BIGSERIAL) para las relaciones, y un código legible para personas y APIs (PAC-000123, CIT-2026-000045), generado con secuencias de PostgreSQL.
  • Borrado lógico. Pacientes, médicos y medicamentos se desactivan con activo = false; nunca se borran, para no romper el historial de citas y fórmulas.
  • Versionado con Flyway. Cada cambio es una migración numerada (V1, V2, V3…), por ejemplo V2__canal_sms.sql agregó el canal SMS/Telegram a notificaciones. La misma historia se aplicó en el contenedor y en Amazon RDS.
